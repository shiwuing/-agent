# 05 · 复盘

## 1. 最难的问题

### 1.1 冲突「可裁决」与「不可裁决」的边界

最容易犯的错误是把「版本更新」当成「优先级更高」：D02 是 2025 年、D01 是 2024 年，似乎应该用 D02 的 15 天。但题目明确要求，缺少适用范围与优先级时不能擅自选择。

最终把裁决顺序固定为：

1. 适用范围匹配（`scope`）
2. 显式优先级（`priority`）
3. 文档明确声明的版本规则（原文出现「以最新版本为准」）
4. 否则请求确认

并用测试锁定：泛问「报销期限」必须 `NEED_CONFIRMATION`；限定「差旅报销期限」才允许使用 D03 的 15 天。

### 1.2 让 Mock 不沦为固定分支

Mock 很容易写成「第一步检索、第二步读取、第三步回答」的硬编码。为了满足 ReAct 要求，`MockLLM.decide(state)` 必须读取 `state.observations`：

- 检索无命中 → 改写查询再检索，而不是直接回答；
- 检索提示冲突 → 读取冲突文档；
- 读取后仍有未读冲突项 → 继续读取；
- 工具失败 → 重试一次后报错；
- 达到步数上限 → 由循环统一返回未完成。

`tests/test_mock_loop.py` 对比正常路径与冲突路径的动作序列，证明不同工具结果导致不同后续动作。

### 1.3 引用校验与答案模板中的文档 ID

回答模板包含 `D04`、`D04-1` 等 ID。最初的数值白名单会把 ID 中的 `04`、`4` 当成「回答中的数字」，导致合法引用被误判。

解决方式：校验前先剔除 `D01`、`D03-2` 这类 ID 模式，再抽取剩余数值，并要求每个数值都出现在引用原文中。

### 1.4 避免「只读一篇冲突文档就回答」

检索返回冲突提示后，如果读取第一篇文档就基于它回答，会违反「不擅自裁决」。最终引入 `pending_conflict`：

- 检索发现冲突 → 记录待处理冲突项；
- 每读完一篇，检查是否还有未读冲突项；
- 全部读完后才进入裁决或请求确认。

### 1.5 短问题被误判为追问

最初的上下文合并规则是「问题不超过 12 字就并入上一轮」。交互测试中，用户先问「云剪辑支持导出哪些格式」，再问「食堂几点开门」，后者被错误合并成「云剪辑… 食堂几点开门」，于是又回答了云剪辑的导出格式；后续「食堂几点开」甚至被上一轮的报销问题带成了冲突确认。

修正：**只有出现明确追问标记**（那 / 它 / 这个 / 上述 / 前面 / 上面 / 刚才 / 那么，或句末「呢」）才合并历史；短但独立的问题保持原样。新增 `tests/test_context.py` 与 `tests/test_acceptance.py` 回归用例锁定该行为。

### 1.6 算力云环境没有系统 Python

远端 `python3` / `pip3` 不在 PATH，实际环境在 `/root/miniconda3`。通过显式使用 `/root/miniconda3/bin/python` 创建 venv，避免依赖交互式 shell 的 PATH。

## 2. 学习收获

1. **Agent 的「决策」必须可观察**：仅看最终答案无法证明 ReAct；Trace 中的动作、参数、观察摘要与后续动作才是证据。
2. **护栏要放在代码层**：冲突裁决与引用校验不能只靠提示词；确定性校验才能在测试中稳定复现。
3. **验收点要翻译成状态机**：把「冲突」「缺口」「失败」「超限」映射为明确状态，测试才有可断言的输出。
4. **Mock 的边界要说清楚**：Mock 能证明流程与护栏，不能证明模型效果；把边界写进文档比夸大结果更可信。
5. **小数据也能做出完整链路**：5 篇合成文档即可覆盖六类验收场景，关键在于场景设计而不是数据规模。
